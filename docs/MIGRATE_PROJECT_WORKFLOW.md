# Project-based migration workflow

`migration-guard migrate` turns the existing Java endpoint analyzer, behavior
graph, replacement planner and RP gates into a project-oriented workflow.

## Case package

```text
cases/<project-id>/
├── profile.json
├── semantic-rules.json
├── compatibility-decisions.json
├── completion-contract.json
├── completion-evidence.template.json
├── fixtures/
└── evidence/
```

- `profile.json` declares source and target roots, language/framework adapters,
  database dialect, entrypoints, runtime contexts and infrastructure boundaries.
- `semantic-rules.json` contains project-owned behavior classification and
  reviewed ownership rules. Class names do not need to be added to the generic
  replacement planner.
- `compatibility-decisions.json` records approved, rejected or pending
  intentional behavior changes.
- `completion-contract.json` is generated by `completion-prepare`. It maps every
  L1-L4 capability signal to fresh, hash-bound evidence controls.
- `completion-evidence.template.json` is a non-passing authoring template. A
  reviewed copy named `completion-evidence.json` can be submitted to the final
  completion gate.
- `fixtures/` contains offline behavior cases.
- `evidence/` contains generated analysis, plans and gate reports.

## Reference source protection

The source package is a read-only reference. The project loader rejects writable
source declarations and any overlap between the source, case package, and target
root. Analysis, Rust scaffolding, and runtime execution capture both Git identity
and a content hash of every configured source directory before work starts, then
fail with `MG-SOURCE-READ-ONLY-VIOLATION` if either changes.

Generated artifacts, fixtures, target code, and collector output must stay in the
case package or independent target root. Runtime tests may seed an isolated data
store, but they must not patch, format, instrument, or generate files in the
reference source directories.

## Commands

```bash
migration-guard migrate init --project <id> --source <java-root> --endpoint <route> --method POST --target-root <rust-root>
migration-guard migrate analyze --project <id> [--strict]
migration-guard migrate runtime-prepare --project <id>
migration-guard migrate runtime-authoring-prepare --project <id>
migration-guard migrate runtime-preflight --project <id>
migration-guard migrate runtime-self-test --project <id>
migration-guard migrate runtime-collector-dry-run --project <id> --spec <collector.draft.json>
migration-guard migrate runtime-fixture-promote --project <id> --entrypoint <id> --scenario <id> --reviewed-by <identity>
migration-guard migrate runtime-collect --project <id> --spec <collector.json> [--output <evidence.json>]
migration-guard migrate runtime-run --project <id>
migration-guard migrate runtime-assemble --project <id> --input <driver-results.json>
migration-guard migrate runtime-gate --project <id> [--evidence <java-runtime-evidence.json>]
migration-guard migrate scaffold --project <id> --target rust
migration-guard migrate offline-gate --project <id>
migration-guard migrate real-gate --project <id> [--evidence <rp-evidence.json>]
migration-guard migrate completion-prepare --project <id> [--force]
migration-guard migrate completion-gate --project <id> [--evidence <completion-evidence.json>]
```

`migrate analyze --strict` uses the project-scale fail-closed defaults
`--max-depth 32 --max-edges 20000` unless either limit is supplied explicitly.
It also exits nonzero when any configured entrypoint remains blocked.

Strict analysis requires the JDK Compiler Tree API structural parser. Each
analysis records the parser backend, JDK version, parsed file count, type and
method declaration counts, and syntax diagnostics. Use
`--structured-parser preferred` for a portable best-effort run or
`--structured-parser off` only for a legacy/non-JDK environment. Required mode
fails closed when the JDK is unavailable, a source file is not parsed, or the
compiler parser reports syntax errors. The existing compatibility analyzer
remains the call-graph engine; the independent JDK parse attests that its input
is structurally valid.

`analyze` resolves the configured source adapter and writes, per entrypoint:

```text
evidence/analysis/<entrypoint-id>/
├── java-analysis.json
├── behavior-graph.json
└── endpoint-replacement-plan.json
```

The offline gate fails when fixtures, graphs or plans are missing, when a plan is
blocked, when entrypoint identity drifts, or when strict compatibility decisions
remain pending.

The real gate additionally requires existing source and target roots plus fresh
RP1-RP6 evidence covering graph closure, contracts, ownership, replay,
concurrency, fault handling, performance, source-off and rollback.
Both analysis and real evidence are bound to a hash of the profile, semantic
rules and compatibility decisions. Editing any of them invalidates stale
evidence until analysis and replay are rerun.

## Capability levels

Migration capability claims are sequential and fail closed:

- `L1`: the reference source is protected by the read-only snapshot guard and
  deep analysis is complete.
- `L2`: offline contracts and compatibility decisions pass.
- `L3`: target implementation checks and the scenario contract pass.
- `L4-A`: dependency protocols have been exercised. Direct SQL or Lua probes
  stop here.
- `L4-B`: a deployable target service and concrete, non-test adapter
  implementations are attested.
- `L4-C`: redacted real evidence and Java/target dual replay pass.
- `L4`: the unified real gate passes with fresh upstream hashes.

A higher-level signal never skips a blocked prerequisite. Container protocol
checks must not be described as a production-ready adapter or deployable
replacement.

Every generated gate report carries its own content hash and, for a real gate,
the exact upstream offline-gate hash. Gate reports also bind the byte-level
digest of every referenced analysis, graph, plan, fixture and runtime evidence
file. Freshness inspection rereads those files and reports post-gate tampering.
Regenerating the offline gate marks any previous real gate stale until the real
gate is rerun.

For strict Rust targets, the real gate writes
`evidence/implementation/production-verification.template.json` and requires a
completed `production-verification.json`. The document is bound to a hash of
`Cargo.toml` and the production Rust sources. It must reference adjacent,
hash-verified logs for a successful `cargo build --locked`, a started runtime
with a 2xx/3xx health observation, and every configured route exercised by the
runtime harness. Templates remain synthetic and cannot pass. Editing production
Rust code after collection invalidates the source hash.

## Project completion contract

`completion-prepare` closes the design gap between a capability label and the
evidence required to claim it. The generated contract always covers source
protection, analysis, offline contracts, implementation checks, scenarios,
dependency protocols, concrete adapters, deployable service startup, real
evidence, dual replay, and the unified release gate.

Projects with batch runtime gates additionally receive mandatory controls for:

- an independent schema-transition client boundary;
- renewable fenced leases;
- idempotent create-table/add-column requests;
- safe batch resume after successful transition;
- DDL timeout, conflict, and partial-failure evidence;
- disposable write scope and marker-bound cleanup verification.

The final L4 controls require verified observability, canary or shadow rollout,
rollback rehearsal, and source-off behavior. These controls are project design
requirements; they do not claim that a target implementation already exists.

Every passing control must reference at least one artifact stored under the case
package or target root. The gate checks artifact hashes, project hash, evidence
age, reference-source path isolation, and secret scanning. A missing, stale,
tampered, unsafe, or secret-bearing artifact blocks its signal. Because levels
are sequential, later evidence cannot skip an earlier blocked control.

Completion artifacts use
`migration-guard.completion-control-evidence/v1`. Each artifact is bound to one
control ID and evidence kind and cannot be reused by another control. L4-C and
L4 controls additionally require an approving reviewer whose identity differs
from the producing identity. Arbitrary JSON files and synthetic or explicitly
non-real evidence are rejected.

`completion-gate` writes `evidence/gates/completion-gate.json`. Its status is
`passed` only when the assessed capability is exactly L4 and every contract
control passes. Otherwise it reports the highest truthful level plus concrete
control IDs that remain blocked.

## Java runtime evidence before services are available

`runtime-prepare` is service-independent. It consumes the latest analysis and
writes:

```text
evidence/runtime/java/
├── runtime-contract.json
├── driver.template.json
├── runtime-evidence.schema.json
├── collectors/
│   ├── mysql.template.json
│   ├── redis.template.json
│   └── events.template.json
└── fixtures/<entrypoint-id>/<scenario-id>.template.json
```

The service-independent authoring step additionally writes:

```text
evidence/runtime/java/
├── environment-contract.json
├── .env.example
└── authoring-report.json
fixtures/java-runtime-drafts/<entrypoint-id>/<scenario-id>/
├── fixture.draft.json
└── collectors/
    ├── mysql.draft.json
    ├── redis.draft.json
    └── events.draft.json
```

`authoring-report.json` is the fixture coverage matrix. It distinguishes
successful artifact generation (`authoringReady`) from promotion readiness and
lists every remaining request or collector placeholder. Collector dry-run is
read-only and does not require a running database, Redis or event stream.

If a redacted
`evidence/runtime/java/deployment-observation.json` using protocol
`migration-guard.runtime-environment-observation/v1` is present, authoring binds
its content hash into the report. Sensitive keys or a missing redaction
declaration block `authoringReady`; credentials stay in process environment or a
secret manager.

The contract is bound to the full Git revision and dirty fingerprint, project
package hash, analysis reports and replacement plans. Changing tracked or
untracked Java source invalidates offline, preflight and runtime evidence.

Real redacted fixtures belong at:

```text
fixtures/java-runtime/<entrypoint-id>/<scenario-id>.json
```

Fixtures are typed as `template`, `specification`, `synthetic`, `draft-runtime`
or `real-runtime`. Offline gates count only valid specification fixtures. Runtime
preflight accepts only `real-runtime` fixtures with `status: ready`,
`realEvidenceEligible: true`, complete lineage and reviewed expectations.
Legacy or unclassified JSON is fail-closed.

Tokens, authorization headers, cookies, passwords, phone numbers and API keys
must not be persisted in these fixtures. They are supplied through environment
variables when the driver runs.

Real fixtures for mutating batch scenarios also require a `writeSafety`
manifest. The scope must be explicitly disposable and approved, list allowed
tenants, panels and tables, cap affected rows, provide a unique marker key and
marker-bound cleanup predicate, require cleanup verification, and carry an
expiry timestamp. Read-only production datasets cannot be promoted as write
fixtures.

`runtime-preflight` verifies:

- project, contract, source and generated-artifact hashes;
- one real redacted fixture for every generated scenario;
- base URL, context, database and Redis environment variables inferred from the
  behavior contracts;
- lifecycle command variables for setup, start, health, seed, invoke, snapshot,
  collect, cleanup and stop, plus fault injection when required.

It performs no mutation and does not claim connectivity. Before the environment
exists, the expected state is `staticReady: true`, `authoringReady: true`,
`executionReady: false` and `evidenceReady: false`. `executionReady` requires all
promoted fixtures and runtime variables; `evidenceReady` requires a validated
real bundle. This preserves fail-closed execution while making pre-service
progress explicit.

`runtime-self-test` generates structurally complete synthetic observations using
the same evidence assembler and hash validator. Synthetic observations are
marked at bundle and scenario level. Relabeling the bundle does not work:
`runtime-gate` requires endpoint-driver provenance, real fixture hashes and no
synthetic markers.

When the environment becomes available, `runtime-run` resolves the prepared
driver command variables and executes:

```text
setup → start → health → seed → invoke → [inject-fault]
      → snapshot → collect → cleanup → stop
```

Cleanup and stop run after failures. `collect` must return the endpoint runtime
observation protocol, dimensions and collector evidence declared by each
scenario. MySQL collection permits only read-only queries and passes credentials
through environment variables; Redis permits only read commands and keeps auth
out of process arguments; the event collector filters JSONL by scenario or
correlation id and persists only approved fields.

For batch workloads, `runtime-gate` additionally evaluates the structured batch
semantics embedded in the observation: planned/valid/failed/committed/undo row
sets, progress monotonicity and conservation, exactly-one terminal, matching
lock owner acquire/release, chunk acceptance, and optional transaction
commit-before-success-terminal ordering. Merely supplying non-empty dimensions
does not pass.

`runtime-gate` proves the
Java baseline only; it does not claim cross-language replay, source-off or final
migration readiness. Those remain under `real-gate`.

## Current adapter boundary

The built-in `java-spring` adapter supports HTTP-route entrypoints and delegates
to the existing Spring/MyBatis-aware Java analyzer. Quarkus, Micronaut,
service-method entrypoints and non-Java sources must register another
`MigrationSourceAdapter`.

The Rust scaffold contains a compileable dependency-free crate and a frozen
`migration-contract.json`. It does not generate business behavior or claim
runtime equivalence.

## Project-defined runtime scenarios

Projects can add domain-specific runtime scenarios in `semantic-rules.json`
without modifying the analyzer-generated replacement plan:

```json
{
  "runtimeScenarios": [
    {
      "id": "calendar-view",
      "entrypointId": "post-api-calendar-page",
      "title": "Calendar view page phase",
      "category": "compatibility",
      "requiredDimensions": ["http", "decisions", "state", "performance"],
      "reason": "Preserve calendar identity, temporal and scale semantics."
    }
  ]
}
```

`runtime-prepare` merges these scenarios with analyzer-generated scenarios.
Duplicate IDs, unknown entrypoints, unsupported categories/dimensions, and
missing descriptions fail closed. Matching `runtimeGates` attach the required
collectors, semantic checks and compatibility decisions.
